# 19. Глоссарий

## 19.1. Предметная область

| Термин | Определение |
|---|---|
| Клиент | Держатель клубной карты, пользователь мобильного приложения. В системе представлен только идентификатором `user_id` |
| Клубная карта | Абонемент клуба. Даёт доступ ко всем групповым занятиям. В MVP не проверяется (A-01) |
| Вид занятия | Тип активности с описанием, уровнем и фиксированной длительностью: йога, зумба, сайклинг, силовая и т. п. |
| Групповое занятие | Сеанс с тренером для нескольких клиентов, вместимость ограничена |
| Персональная тренировка | Занятие тренера с одним клиентом. В системе это бронь времени тренера, цену и оплату клиент и тренер согласуют напрямую |
| Сеанс | Конкретное занятие в расписании: дата, время, тренер, зал, вместимость. Единая сущность для групповых занятий и персональных слотов |
| Слот | Сеанс персональной тренировки, который тренер открыл для онлайн-записи |
| Вместимость | Максимальное число участников сеанса. Для персональной тренировки равна 1 |
| Запись | Факт того, что клиент занял место на сеансе. Имеет статус и историю |
| Горизонт записи | Насколько вперёд доступно расписание и запись: 14 дней |
| Окно записи | Период, когда на сеанс можно записаться: групповое — до начала, персональное — не позже чем за 24 часа |
| Дедлайн отмены | Последний момент, когда клиент может отменить запись: групповое — за 30 минут, персональное — за 24 часа до начала |
| Свободная отмена | Право отменить запись вне дедлайна, до начала сеанса. Появляется после замены тренера на групповом занятии |
| Отмена клубом | Отмена сеанса по решению клуба, например из-за болезни тренера. Все записи переходят в «Отменена клубом» |
| Овербукинг | Ситуация, когда записей на сеанс больше, чем мест. Система её исключает |
| Операция клуба | Действие над расписанием (отмена сеанса, замена тренера), которое выполняет тех. специалист через служебный API |
| Мастер-данные | Справочники и расписание: залы, тренеры, виды занятий, сеансы. Загружаются техническими средствами |

## 19.2. Аналитика и архитектура

| Термин | Определение |
|---|---|
| BRD | Business Requirements Document, документ бизнес-требований |
| BG / BR / UR / FR / NFR | Бизнес-цель / бизнес-требование / пользовательское / функциональное / нефункциональное требование |
| UC | Use Case, вариант использования: сценарий взаимодействия актора с системой |
| US | User Story, пользовательская история: единица бэклога с критериями приёмки |
| EC | Edge Case, краевой кейс |
| MoSCoW | Приоритизация: Must, Should, Could, Won't |
| Gherkin | Формат критериев приёмки «Дано / Когда / Тогда» |
| DoR / DoD | Definition of Ready / Definition of Done — критерии готовности истории к работе и к сдаче |
| BPMN | Нотация моделирования бизнес-процессов |
| C4 | Модель описания архитектуры по уровням: контекст, контейнеры, компоненты, код |
| ADR | Architecture Decision Record, запись архитектурного решения |
| Атомарность | Свойство операции выполниться целиком или не выполниться вовсе |
| Идемпотентность | Свойство операции давать тот же результат при повторном вызове. Реализуется ключом `Idempotency-Key` |
| Transactional Outbox | Паттерн: событие записывается в таблицу в той же транзакции, что и изменение данных, а отправляется отдельным процессом |
| Exclusion-ограничение | Ограничение PostgreSQL, запрещающее пересечение значений (например, временных интервалов) между строками |
| APNs / FCM | Сервисы доставки push-уведомлений Apple и Google |
| OIDC / JWT / JWKS | Протокол аутентификации / формат токена / набор публичных ключей для проверки токена |
| p95 | 95-й перцентиль: значение, которое не превышают 95 % измерений |
| RPO / RTO | Допустимая потеря данных / допустимое время восстановления после сбоя |
