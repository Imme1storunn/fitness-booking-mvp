# 07. Функциональные требования

Функциональное требование (`FR`) описывает **поведение системы**: что она принимает, что проверяет и что возвращает. Формулировка: «Система должна…». Параметры в фигурных скобках (`{group_cancel_deadline}`) берутся из настроек (FR-30), значения по умолчанию указаны в таблице 7.9.

## 7.1. Аутентификация и доступ

| ID | Требование | UR / BR | Приоритет | Критерий приёмки |
|---|---|---|---|---|
| FR-01 | Система должна принимать запросы клиента только с токеном доступа, валидировать его через внешний сервис аутентификации и извлекать из него идентификатор пользователя (`user_id`). | BR-17 | Must | Запрос без токена или с невалидным / просроченным токеном получает `401`. Валидный — обрабатывается от имени `user_id` из токена. |
| FR-02 | Система не должна хранить персональные данные клиента, кроме `user_id` и токенов устройств для push. | — | Must | В модели данных нет ФИО, телефона, email клиента. |
| FR-03 | Система должна давать клиенту доступ только к его собственным записям и уведомлениям. | UR-08 | Must | Обращение к чужой записи возвращает `404` (факт существования не раскрывается). |

## 7.2. Расписание

| ID | Требование | UR / BR | Приоритет | Критерий приёмки |
|---|---|---|---|---|
| FR-04 | Система должна возвращать список сеансов на выбранную дату в часовом поясе клуба. Дата должна быть в диапазоне [сегодня; сегодня + `{booking_horizon_days}` − 1]. | UR-01 | Must | Для даты вне диапазона возвращается `400 OUT_OF_HORIZON`. Уже начавшиеся сеансы и сеансы в статусе «Отменён» в выдачу не попадают. |
| FR-05 | Для каждого группового сеанса система должна возвращать число свободных мест (`capacity − booked_count`) и состояние записи для текущего клиента: `OPEN`, `FULL`, `CLOSED`, `BOOKED_BY_ME`. | UR-02 | Must | Состояние вычисляется на момент запроса с учётом правил FR-09…FR-12. |
| FR-06 | Персональные слоты, которые заняты или недоступны из-за занятости тренера (FR-13), не должны показываться в расписании. Исключение — слот, забронированный текущим клиентом: он показывается как `BOOKED_BY_ME`. | UR-02, UR-06 | Must | После бронирования слот 18:00–19:00 исчезает из расписания у других клиентов вместе с пересекающимся слотом того же тренера 18:30–19:30. |
| FR-07 | Система должна поддерживать фильтры по типу, виду занятия, тренеру и уровню. Фильтры объединяются по «И», сортировка — по времени начала, затем по названию вида. | UR-03 | Should | Фильтр «Йога» + «Иванов» возвращает только сеансы йоги Иванова на выбранную дату. |
| FR-08 | Система должна возвращать карточку сеанса: вид и его описание, тип, уровень, тренер, зал, начало и окончание, вместимость, свободные места, состояние записи. Для персонального — признак «оплата по договорённости с тренером». | UR-04 | Must | Все перечисленные поля есть в ответе. Для отменённого сеанса возвращается статус `CANCELLED`. |

## 7.3. Создание записи

**Порядок проверок при записи** (первая сработавшая проверка определяет причину отказа):

| Шаг | Проверка | Код отказа |
|---|---|---|
| 1 | Сеанс существует | `404 SESSION_NOT_FOUND` |
| 2 | Сеанс не отменён | `409 SESSION_CANCELLED` |
| 3 | Начало сеанса не дальше горизонта записи | `409 OUT_OF_HORIZON` |
| 4 | Окно записи открыто: групповое — до начала, персональное — не позже чем за `{personal_booking_close}` | `409 BOOKING_CLOSED` |
| 5 | У клиента нет активной записи на этот сеанс | `409 ALREADY_BOOKED` |
| 6 | У клиента нет активной записи, пересекающейся по времени | `409 CLIENT_TIME_CONFLICT` |
| 7 | Только для персонального: у тренера нет пересекающегося занятия | `409 TRAINER_BUSY` |
| 8 | Есть свободное место (атомарно) | `409 SESSION_FULL` |

| ID | Требование | UR / BR | Приоритет | Критерий приёмки |
|---|---|---|---|---|
| FR-09 | Система должна создавать запись клиента на сеанс, выполняя проверки 1–8 в указанном порядке. При успехе запись получает статус «Активна» (`ACTIVE`), а `booked_count` сеанса увеличивается на 1. | UR-05, UR-06, BR-03, BR-04 | Must | Успешный ответ `201` с созданной записью. При отказе — код из таблицы выше, запись не создаётся, счётчик не меняется. |
| FR-10 | Занятие места и создание записи должны выполняться атомарно в одной транзакции: место занимается только при условии `booked_count < capacity`. | BR-05 | Must | 500 параллельных запросов на сеанс с 25 местами дают ровно 25 записей `ACTIVE` и `booked_count = 25`. |
| FR-11 | На уровне БД должно быть гарантировано не более одной активной записи клиента на сеанс. | BR-06 | Must | Попытка вставить вторую активную запись отклоняется ограничением уникальности даже в обход прикладных проверок. |
| FR-12 | Пересечение интервалов определяется как `start_A < end_B и start_B < end_A`, то есть интервалы полуоткрытые `[start; end)`. | BR-08 | Must | Занятия 18:00–19:00 и 19:00–20:00 не пересекаются. 18:00–19:00 и 18:30–19:30 пересекаются. |
| FR-13 | Для персонального слота тренер считается занятым, если у него есть неотменённый групповой сеанс или персональный слот с активной записью, пересекающийся по времени. | BR-07 | Must | Запись на слот, пересекающийся с групповым сеансом того же тренера, отклоняется с `TRAINER_BUSY`. |
| FR-14 | Повторный запрос создания записи с тем же ключом идемпотентности (`Idempotency-Key`) в течение 24 часов должен возвращать результат первого запроса и не создавать новую запись. | BR-06 | Must | Двойное нажатие «Записаться» даёт одну запись. Оба ответа содержат одинаковый `booking_id`. |
| FR-15 | После успешной записи система должна создать уведомление «Запись подтверждена» и запланировать напоминание (FR-26). | UR-11 | Must | Уведомление появляется в ленте клиента не позднее 10 секунд после записи. |

## 7.4. Отмена записи клиентом

| ID | Требование | UR / BR | Приоритет | Критерий приёмки |
|---|---|---|---|---|
| FR-16 | Система должна позволять клиенту отменить свою запись в статусе `ACTIVE`, если текущее время не позже `start − {deadline}`. Для группового `{deadline}` = `{group_cancel_deadline}`, для персонального — `{personal_cancel_deadline}`. | UR-09, BR-09 | Must | Групповое в 19:00 отменяется в 18:30:00 и не отменяется в 18:30:01 (`409 CANCELLATION_DEADLINE_PASSED`). Время проверяется по серверным часам. |
| FR-17 | Если у записи установлен признак свободной отмены (заменён тренер, FR-23), дедлайн не применяется: отмена возможна до начала сеанса. | UR-10, BR-14 | Should | Запись с признаком отменяется за 5 минут до начала. |
| FR-18 | При отмене система должна атомарно перевести запись в статус «Отменена клиентом» (`CANCELLED_BY_CLIENT`) и уменьшить `booked_count` сеанса на 1. | BR-10 | Must | При параллельных отменах и записях `booked_count` всегда равен числу активных записей сеанса. |
| FR-19 | Повторная отмена уже отменённой клиентом записи должна возвращать текущее состояние записи без изменений. Отмена записи в статусе `COMPLETED` или `CANCELLED_BY_CLUB` отклоняется. | — | Should | Повтор даёт `200` с тем же статусом, счётчик не меняется. Для других статусов — `409 BOOKING_NOT_ACTIVE`. |
| FR-20 | После отмены система должна создать уведомление «Запись отменена» и отменить запланированное напоминание. | UR-11 | Must | Напоминание по отменённой записи не приходит. |
| FR-21 | После отмены клиент может снова записаться на тот же сеанс по общим правилам FR-09. | — | Should | Новая запись создаётся с новым `booking_id`, старая остаётся в истории. |

## 7.5. Изменения со стороны клуба (технические операции)

| ID | Требование | UR / BR | Приоритет | Критерий приёмки |
|---|---|---|---|---|
| FR-22 | Операция отмены сеанса (любого типа) должна в одной транзакции перевести сеанс в статус `CANCELLED`, все его активные записи — в `CANCELLED_BY_CLUB`, обнулить `booked_count`, создать уведомления клиентам и отменить напоминания. | UR-14, BR-13 | Must | После операции у сеанса нет активных записей. Записи в других статусах не меняются. Каждый затронутый клиент получает уведомление. |
| FR-23 | Операция замены тренера применима только к групповому сеансу. Она должна проверить, что новый тренер свободен на интервале сеанса, сменить тренера, установить активным записям признак свободной отмены и создать уведомления с именем нового тренера. | UR-14, BR-14 | Should | Если новый тренер занят, операция отклоняется. Для персонального слота операция отклоняется, вместо неё используется FR-22. |
| FR-24 | Изменение вместимости сеанса ниже текущего `booked_count` и изменение времени сеанса с активными записями должны отклоняться. | UR-13 | Must | Для переноса занятия сеанс отменяется (FR-22) и создаётся новый. |
| FR-25 | Система должна не реже чем раз в 5 минут переводить активные записи на завершившиеся сеансы (`end ≤ now`) в статус `COMPLETED`. | BR-12 | Should | Через 15 минут после окончания сеанса у него нет записей `ACTIVE`. |

## 7.6. Уведомления

| ID | Требование | UR / BR | Приоритет | Критерий приёмки |
|---|---|---|---|---|
| FR-26 | Система должна отправлять напоминание за `{reminder_offset}` до начала по каждой активной записи. Если запись создана позже этого момента, напоминание не планируется. | BR-16 | Should | При записи в 18:00 на занятие в 19:00 напоминание не приходит. Точность отправки ±5 минут. |
| FR-27 | Система должна создавать уведомления типов: `BOOKING_CONFIRMED`, `BOOKING_CANCELLED`, `SESSION_CANCELLED`, `TRAINER_CHANGED`, `REMINDER`. Каждое сохраняется в ленте и отправляется push на все зарегистрированные устройства клиента через APNs / FCM. | UR-11, BR-15 | Must | Уведомление есть в ленте независимо от результата отправки push. |
| FR-28 | При сбое отправки push система должна повторить её до 3 раз с нарастающей задержкой. Недействительный токен устройства удаляется. Сбой push не влияет на запись. | BR-15 | Should | При недоступности FCM запись создаётся успешно, уведомление остаётся в ленте. |
| FR-29 | Система должна позволять регистрировать токен устройства, получать ленту уведомлений со счётчиком непрочитанных и отмечать уведомления прочитанными. | UR-11 | Must | После отметки счётчик непрочитанных уменьшается. |

## 7.7. Настройки

| ID | Требование | UR / BR | Приоритет | Критерий приёмки |
|---|---|---|---|---|
| FR-30 | Параметры правил записи должны храниться в настройках системы и применяться к новым операциям без перезапуска и выпуска новой версии. | UR-15, BR-11 | Should | Изменение `{group_cancel_deadline}` с 30 на 60 минут применяется к отменам не позднее чем через 1 минуту. |

## 7.8. Учёт и отчётность

| ID | Требование | UR / BR | Приоритет | Критерий приёмки |
|---|---|---|---|---|
| FR-31 | Система должна фиксировать каждое изменение статуса записи: время, новый статус, инициатор (`CLIENT`, `SYSTEM`, `CLUB`). | BR-18 | Must | По истории любой записи восстанавливается её жизненный цикл. |
| FR-32 | Система должна журналировать отказы в записи с кодом причины, сеансом и `user_id`. | BR-18 | Should | Выгрузка «отказы по причинам за период» строится запросом к БД. |

## 7.9. Параметры по умолчанию

| Параметр | Значение | Где используется |
|---|---|---|
| `booking_horizon_days` | 14 дней | FR-04, проверка 3 |
| `group_booking_close` | 0 мин (до начала) | проверка 4 |
| `personal_booking_close` | 24 ч | проверка 4 |
| `group_cancel_deadline` | 30 мин | FR-16 |
| `personal_cancel_deadline` | 24 ч | FR-16 |
| `reminder_offset` | 2 ч | FR-26 |
| `club_timezone` | Europe/Moscow | FR-04 |
